## 1. 제작한 것

처음에는 제주 낚시 포인트를 한눈에 보는 간단한 지도 웹앱으로 시작했습니다. 검색과 어종·낚시 방법 필터를 만들고, 즐겨찾기와 현재 위치에서 가까운 포인트 찾기를 추가했습니다. 출조 전에 같이 볼 수 있도록 주변 화장실, 날씨, 해상 상태와 공식 물때도 붙였습니다.
이후에는 장소를 찾는 데서 끝내지 않고 잡은 어종을 남기는 「나의 낚시 도감」으로 확장했습니다. 도감은 31종이며, 미수집 어종은 회색으로 보이고 첫 조과를 등록하면 컬러로 바뀝니다.
사진·날짜·마릿수·장소·메모를 저장하고, 어종별 총 마릿수와 기록 횟수를 확인할 수 있습니다. 기록을 모아 보는 조과 통계와 다음 목표를 보여주는 24개 업적 / 배지도 추가했습니다.

## 3. PRD

기존 지도에 도감을 붙이기 전에, 어떤 기능을 넣고 어디까지 만들지 PRD로 정했습니다. 로그인이나 동기화처럼 이번에 다루기 어려운 기능도 여기서 구분했습니다.

[PRD 전체 보기](./PRD.md)

- 제주 낚시 포인트 지도와 어종·낚시 방법 정보
- 어종별 이미지, 특징, 채비와 관련 포인트 안내
- 사진·날짜·마릿수·장소·메모를 남기는 조과 기록
- 첫 기록 컬러 해금과 마지막 기록 삭제 후 회색 복귀
- IndexedDB에 사진과 기록 저장, 새로고침 후 복원
- PC와 모바일 브라우저에서 사용할 수 있는 화면

조과 통계, 장소 선택, 업적 / 배지는 나중에 F9~F11로 추가했습니다.

## 6. GitHub 작업 방식

## 7. Agent Skills

어종 자료, 사진 저장, 지도 연결은 확인할 항목이 서로 달랐습니다. 반복해서 확인할 순서를 프로젝트 전용 Skill 네 개로 적어 두고, 해당 작업을 맡길 때 읽고 적용하도록 했습니다.
Skill을 만드는 것과 실제 기능에 사용하는 것은 구분해서 [사용 기록](./docs/SKILL_USAGE.md)에 남겼습니다.

### fish-catalog-manager

**만든 이유**

어종을 늘릴 때 이름·이미지·출처·지도 연결 키를 빠뜨리지 않으려고 만들었습니다. 이미지를 고를 때 형태와 사용 조건도 같이 보도록 했습니다.

**SKILL.md 핵심 내용**

- `name: fish-catalog-manager`
- `description`: 어종·두족류 데이터, 필수 필드, 지도 키, 이미지 출처와 회색 잠금 표시를 검사할 때 사용합니다.
- 절차: 실제 도감 원본 확인 → 필수 필드·중복 ID 검사 → 실제 지도 필터와 `mapSpeciesKey` 대조 → 이미지·출처 확인 → 검증 후 사용 기록 작성.
- 자료·스크립트: `species-schema.md`, `image-source-policy.md`, `validate-catalog.mjs`. 확인하지 못한 자료는 추정해서 채우지 않습니다.

[전체 SKILL.md 보기](./skills/fish-catalog-manager/SKILL.md)

**실제 사용한 곳**

31종의 데이터·이미지와 지도 키를 검사했습니다. 배경이 포함된 사진이나 잘린 이미지를 교체하고, 이미지 준비 중으로 남겼던 항목을 보완했습니다.
`학공치`와 지도 표기 `학꽁치`처럼 이름이 다른 경우도 실제 필터와 대조했습니다.

### catch-record-manager

**만든 이유**

사진 저장과 마릿수 계산이 어긋나면 도감 해금도 함께 틀어집니다. 등록뿐 아니라 수정·삭제·새로고침까지 같은 기준으로 확인하려고 만들었습니다.

**SKILL.md 핵심 내용**

- `name: catch-record-manager`
- `description`: IndexedDB 조과 기록의 추가·수정·삭제, 사진, 누적 마릿수·기록 횟수·수집률과 잠금/해금을 다룹니다.
- 절차: 실제 DB 구조 확인 → 날짜·마릿수·사진 검사 → 저장 작업 완료 후 화면 반영 → 유효 기록 재집계 → 사진·기록 복원 확인.
- 자료·스크립트: `indexeddb-schema.md`, `validate-record-logic.mjs`. 첫 기록은 해금, 마지막 기록 삭제는 잠금인지 확인하고 저장 실패 시 입력을 보존합니다.

[전체 SKILL.md 보기](./skills/catch-record-manager/SKILL.md)

**실제 사용한 곳**

2마리 + 3마리 = 총 5마리 / 기록 2회, 수정·삭제 후 재계산을 검사했습니다.
이후 통계·장소 선택·업적 작업에도 적용해 장소 ID 연결과 `achievementUnlocks` 저장소를 확인했습니다. DB 버전이 바뀌어도 기존 사진과 기록이 남는지 검사했습니다.

### map-catalog-integrator

**만든 이유**

**실제 사용한 곳**

무늬오징어·한치 상세의 실제 지도 URL과 `species` 값을 검사했습니다.
어종 필터·관련 마커, 직접 접속·새로고침·뒤로가기를 확인했습니다. 양방향 연결을 줄인 뒤에는 Popup의 기존 정보가 유지되는지도 다시 봤습니다.

## 8. 개발 방법

아이디어 → PRD → TODO → Skill → 기능 구현 → 직접 실행 / 테스트 → Commit / Push → 다음 Todo

Codex에 앱 전체를 한 번에 요청하기보다, TODO의 한 단계와 그때 유지할 기능을 같이 설명했습니다.
문제가 생기면 오류 메시지와 실제 화면을 보고 수정한 뒤 같은 흐름을 다시 실행했습니다. 새 기능을 추가하는 작업과 이미 만든 기능을 다시 확인하는 작업을 반복했습니다.

### PRD / TODO / Skill 사용 전후 차이

| 구분 | 처음 계획·상태 | 실제 개발 방식 |
| --- | --- | --- |
| 기능 범위 | 지도·검색·어종 필터 중심 | 도감 확장 전에 PRD로 포함·제외 범위를 정하고 후속 기능은 별도 요구사항으로 추가 |
| 작업 순서 | 초기 TODO 다섯 항목 | 도감 C01~C07과 통계·장소·업적 작업으로 나눠 진행 |
| AI 요청 | 기본 화면·지도 등 큰 기능 단위 | Phase별 작업과 보존할 데이터·기능, 완료 확인 조건을 함께 요청 |
| 검증 | 기존 지도 기능 검사 | Skill의 같은 절차로 도감·저장·연결을 반복 확인하고 실패도 기록 |
| Git | 기존 지도 저장소와 기능별 커밋 | 같은 저장소에서 도감·통계·업적도 작업 단위 Commit/Push |
| 수정 기록 | 초기 TODO의 완료 여부 표시 | 발견한 오류, 바꾼 이유와 재검사 범위를 함께 기록 |

작업이 늘어나니 완료 표시만으로는 어디까지 확인했는지 알기 어려웠습니다.
TODO와 Skill 사용 기록을 같이 남긴 뒤에는 오류가 났던 부분과 아직 확인하지 않은 부분을 다시 찾기 편했습니다.

## 9. 느낀점

처음에는 Codex가 코드를 만들어주면 거의 끝일 거라고 생각했는데, 막상 해보니까 내가 원하는 결과가 맞는지 직접 확인하는 과정이 계속 필요했습니다. 특히 어종 이미지는 출처가 있는 이미지여도 실제 화면에 넣어보면 몸이 잘리거나 배경이 남아 있는 경우가 있어서 여러 번 다시 골라야 했습니다. 좌표도 그냥 비슷한 위치를 넣기보다는, 직접 확인하지 못한 곳은 비워 두는 게 더 낫다고 생각했습니다.
기록 기능을 추가했을 때는 새로 만든 JS 파일이 404 오류가 나면서 도감 전체가 안 뜬 적도 있었습니다. 그때 새로 만든 기능만 확인하는 게 아니라 기존 기능도 같이 테스트해야 한다는 걸 알게 됐습니다.
TODO를 나눠서 하나씩 작업하니까 문제가 생겼을 때 어디부터 확인해야 할지 찾기가 훨씬 편했습니다. Skill에 자주 확인해야 하는 순서를 적어 둔 것도 반복 작업할 때 도움이 됐고, 코드가 돌아간다고 끝내지 않고 실제 화면에서 기록이나 사진이 제대로 저장되는지도 직접 확인했습니다.
Git 기록을 다시 보면서는 완성된 기능만 남기는 것보다, 중간에 어떤 기능을 추가했고 어떤 부분을 수정하거나 뺐는지도 같이 기록해 두는 게 중요하다고 느꼈습니다. 이번 과제를 하면서 AI가 코드를 빠르게 만들어주는 것도 중요하지만, 결국 결과를 확인하고 방향을 정하는 건 직접 해야 한다는 점을 가장 많이 느꼈습니다.

## 10. 결론

처음에는 제주 낚시 포인트만 보여주는 지도를 만들려고 했는데, 만들다 보니 도감이랑 조과 기록, 통계, 업적 기능까지 점점 추가하게 됐습니다. 처음 계획했던 기능보다 많아졌고, 반대로 지도 Popup의 도감 링크처럼 직접 넣어봤다가 화면이 복잡해져서 다시 뺀 기능도 있었습니다.
Vibe Coding을 하면서 평소라면 어렵게 느꼈을 기능도 빠르게 시도해볼 수 있었습니다. 대신 AI가 만들어준 결과가 항상 원하는 형태로 나오는 건 아니어서, 직접 실행해보고 문제가 있으면 다시 요청을 고치는 과정이 계속 필요했습니다.
PRD와 TODO를 사용하니까 지금 무엇을 만들고 있는지 정리하기 편했고, Skill과 Git 기록을 남기면서 어떤 작업을 했고 어디까지 확인했는지도 다시 보기 쉬웠습니다. 지금은 Render에 배포해서 브라우저에서 실제로 실행할 수 있는 상태까지 만들었습니다.
이번 과제를 하면서 AI를 이용하면 개발 속도는 확실히 빨라질 수 있지만, 기능을 정하고 결과를 확인하고 수정하는 과정은 결국 직접 해야 한다는 점을 배웠습니다.

## 주의사항 및 출처

- 날씨·해상·물때는 참고용입니다. 실제 출조 전에는 기상특보와 현장 상황을 확인해야 합니다.
- 개인 메모의 안전 관련 표현은 작성 당시의 경험이며 현재 상태를 보장하지 않습니다.
- 조과 사진과 기록은 현재 브라우저의 IndexedDB에 저장됩니다. 사이트 데이터를 지우면 사라질 수 있습니다.
- 기기 간 자동 동기화는 없습니다. 로컬 실행 주소와 Render 사이트의 저장 기록도 서로 다릅니다.

지도는 [MapLibre](https://maplibre.org/)와 [OpenFreeMap](https://openfreemap.org/), 날씨·해상은 [Open-Meteo](https://open-meteo.com/)와 [Marine API](https://open-meteo.com/en/docs/marine-weather-api), 물때는 [국립해양조사원 조석예보](https://www.data.go.kr/data/15156018/openapi.do)를 사용했습니다.
화장실은 [제주시 공중화장실 자료](https://www.data.go.kr/data/15110521/fileData.do)와 성산·남원 주변 보조 자료를 정리했습니다.
포인트 좌표와 자료 범위는 [구현·데이터 기록](./docs/TECHNICAL_NOTES.md)에 남겼습니다.
